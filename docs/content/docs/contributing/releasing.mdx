This page is for maintainers of weebo-forgejo. To install a release, see
[Install](/docs/guides/install).

Versions come from the commit history: commits follow Conventional
Commits (enforced by [cocogitto](https://docs.cocogitto.io/) on every
commit), and `cog bump --auto` derives the next version from them.

## What a release produces

For a tag `vX.Y.Z`, `publish.yml` pushes:

| Artifact | Where |
| --- | --- |
| Operator image (distroless) | `ghcr.io/batleforc/weebo-forgejo-operator:vX.Y.Z` (+ `latest`) |
| Operator image (Red Hat hardened) | `…:vX.Y.Z-hardened` (+ `hardened`) |
| Helm chart | `oci://ghcr.io/batleforc/charts/weebo-forgejo`, version `X.Y.Z` |

Both images also contain `weebo-forgejo-importer`
([Migrating](/docs/guides/migration)). `latest`/`hardened` only move when
the tag is the highest version. Each pushed image is scanned by trivy
(HIGH/CRITICAL fail the job) and smoke-run before the job succeeds.

## Bumping

`cog bump` runs `.hooks/bump-versions.sh`, which writes the version into
`Cargo.toml` (`[workspace.package]`), `Cargo.lock` and `Chart.yaml`
(`version` and `appVersion`), commits, tags and updates `CHANGELOG.md`.

**Locally (signed commits)** — the default when `main` requires signed
commits:

```bash
cog bump --auto --dry-run   # shows the next version
cog bump --auto             # bump commit + tag, signed by your git config
git push origin main --follow-tags
```

The pushed tag triggers `publish.yml`.

**From GitHub** — run the *Release* workflow manually. It bumps with the
workflow's token, pushes the commit and tag, then calls `publish.yml` for
that tag (a tag pushed with the workflow token triggers no other
workflow). This only works if `main` accepts the bot's unsigned commit.

To publish an existing tag again (e.g. after a registry hiccup), run
`publish.yml` manually with that tag.

## Before releasing

| Check | Where |
| --- | --- |
| Lint, unit, contract and envtest tests, generated files up to date, chart lint, audit, both images build and run | `ci.yml`, every push |
| kind end to end with both images: golden path, admission denials, leader failover, deletion policies | `e2e.yml`, weekly and on demand — run it before a release |
| Every layer under coverage, live suites included (≥ 85% of lines) | `ci.yml` job `coverage`, every push |
| Against a real Forgejo: gateway, controllers, importer | `task test:live-forgejo` |

The kind e2e runs locally too with a working container engine:
`task e2e` (`ENGINE=podman` to build with podman). For the live suites and
coverage: `task forgejo:container:start ENGINE=podman` (writes
`.forgejo-test.env`), then `task coverage` or `task test:live-forgejo`.

## The documentation site

This site is published to GitHub Pages by `docs-pages.yml` on every push to
`main` that touches `docs/` or the CRDs, and can be re-run by hand. It's a
static export (`output: 'export'`); the workflow sets `DOCS_BASE_PATH` to
`/weebo-forgejo` for the project-site sub-path. Locally, `task docs` runs the
dev server and `task docs:build` builds and lints it at the root.
