description: Issue OAuth2 client credentials and access tokens into Secrets or Vault.

## OAuth2 applications

For apps that log in **with Forgejo** (Grafana, Argo CD...):

```yaml
apiVersion: forgejo.weebo.io/v1alpha1
kind: ForgejoOAuth2Application
metadata:
  name: grafana
  namespace: monitoring
spec:
  ownerRef: { name: sso-bot }    # optional; the admin account otherwise
  redirectUris:
    - https://grafana.example.com/login/generic_oauth
```

The `grafana` Secret receives `FORGEJO_CLIENT_ID`,
`FORGEJO_CLIENT_SECRET` and `FORGEJO_URL` (the OIDC issuer).

Forgejo regenerates the client secret on **every** update and never shows
it again, so the operator only updates the application when the spec
really differs, when a target lost the secret, or on rotation:

```bash
kubectl -n monitoring annotate fjoauth grafana \
  forgejo.weebo.io/rotate-secret=$(date +%s) --overwrite
```

## Access tokens

```yaml
apiVersion: forgejo.weebo.io/v1alpha1
kind: ForgejoAccessToken
metadata:
  name: ci
  namespace: team-a
spec:
  userRef: { name: ci-bot }
  scopes: [write:repository]
  repositoryRefs: [{ name: app }]   # optional restriction
  rotationPeriod: 720h
```

With `repositoryRefs`, Forgejo only accepts the `read:`/`write:`
`issue` and `repository` scopes (anything else is `InvalidSpec`).

The Secret gets `FORGEJO_TOKEN`, `FORGEJO_USERNAME`, `FORGEJO_URL`. A new
token is issued (the old one revoked first) when `rotationPeriod` elapses,
on a `rotate-secret` nonce, or when a target loses it. Changing `scopes`
or `repositoryRefs` issues a new token too, which needs the
`allow-disruptive-update` annotation.

<Callout type="warn">
Restrict `allowedUsers` in your [ForgejoNamespacePolicy](/docs/guides/allow-list):
without it, any namespace allowed to create tokens can mint one for any
user — including privileged ones.
</Callout>

## Secret targets

Every kind that emits a secret takes `secretTargets`; the value is written
to each of them:

```yaml
secretTargets:
  - name: ci-token                 # Kubernetes Secret in the CR's namespace
  - name: ci-token
    namespace: ci-runners          # ...or another namespace
  - backend: vault
    name: ci-token                 # <pathPrefix>/<namespace>/ci-token
  - backend: vault
    name: unused
    path: ci/team-a/forgejo        # explicit KV v2 path
```

Without `secretTargets`, one target named after the CR is used, on the
instance's default backend. Kubernetes Secrets are applied server-side,
labelled `app.kubernetes.io/managed-by: weebo-forgejo`, and deleted with
their CR. Vault writes are skipped when the stored document is identical,
so steady-state reconciles never pile up KV versions.
