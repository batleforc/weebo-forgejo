---
title: Migrating an existing Forgejo
description: Bring users, organizations, teams, repositories, webhooks and deploy keys that already exist under the operator with the importer.
---

The operator never adopts an object by name: a CR whose name is already
taken in Forgejo stays `Ready: False` / `ForgejoObjectAlreadyExists`. The
only way to bring existing objects under management is
**`weebo-forgejo-importer`**, which reads the live instance and writes the
matching CRs **with the Forgejo id already recorded in their status** —
the operator then manages that exact object instead of trying to create
it.

## What gets imported

| Forgejo | CR | Notes |
| --- | --- | --- |
| Users | `ForgejoUser` | `managementPolicy: Observe` by default (see below) |
| Organizations | `ForgejoOrganization` | |
| Teams + members | `ForgejoTeam` | `Owners` is skipped (Forgejo manages it) |
| Repositories | `ForgejoRepository` | settings, units, branch protections, team access; pull mirrors keep their `migrate.mirrorInterval` |
| Repository and organization webhooks | `ForgejoWebhook` | without `secretRef` (see below) |
| Deploy keys | `ForgejoDeployKey` | with their `publicKey` |

OAuth2 applications and access tokens are not imported: their secrets
can't be read back, so the operator could never hand them out. Recreate
them as CRs.

Every imported CR has **`deletionPolicy: Orphan`** — these objects existed
before the operator, and deleting a manifest must not destroy them. Switch
to `Delete` per CR once you want that.

## Running it

The importer needs a site-administrator token (read access is enough) and,
with `--apply`, a kube context allowed to create the CRs and patch their
`status` (cluster-admin, typically). It ships in the operator image; run
it from a workstation with your kubeconfig mounted:

```bash
docker run --rm -e FORGEJO_TOKEN \
  -v "$HOME/.kube/config:/kubeconfig:ro" -e KUBECONFIG=/kubeconfig \
  --entrypoint /usr/local/bin/weebo-forgejo-importer \
  ghcr.io/batleforc/weebo-forgejo-operator:<version> \
  --url https://git.example.com --namespace forgejo --owner weebo
```

(or `cargo run -p importer --` from a checkout). Options:

| Flag | Default | |
| --- | --- | --- |
| `--url` / `FORGEJO_URL` | | Instance URL, as in `ForgejoInstance.spec.url` |
| `--token` / `FORGEJO_TOKEN` | | Site-administrator token |
| `--namespace`, `-n` | `default` | Namespace of the repositories, webhooks and deploy keys |
| `--instance-ref` | none | Written as `spec.instanceRef` |
| `--owner` (repeatable) | everything | Only these organizations/users and their repositories; other users are imported only when a team or repository references them |
| `--manage-users` | off | Import users as `Manage` instead of `Observe` |
| `--apply` | off | Create the CRs and seed their status (otherwise print YAML) |

Warnings (a member that isn't a known user, a team left out of a
repository's `teamRefs`...) go to stderr.

## The safe order: apply, then commit

`status` is a subresource: `kubectl apply` and GitOps tools never write
it. The adoption therefore happens in the cluster, once:

1. **Review** what would be imported:
   `weebo-forgejo-importer ... > forgejo.yaml`.
2. **Adopt**: run the same command with `--apply`. Each CR is created
   with the `forgejo.weebo.io/import-pending` annotation — the operator
   leaves it alone — then its `status.forgejoId`/`forgejoName` are
   written, then the annotation is removed. The operator never sees an
   imported CR without its id, so it can't create a duplicate (webhooks
   have no unique name to collide on).
3. **Commit** `forgejo.yaml` to your GitOps repository. Its `status`
   blocks are ignored when applied; the CRs already exist with their ids.

Re-running `--apply` is safe: a CR that already owns the same object is
skipped; one owning a different object is reported as an error and left
untouched. A CR that existed *without* an id (e.g. one stuck on
`ForgejoObjectAlreadyExists`) is taken over and adopted.

The first reconcile of an adopted CR sends nothing to Forgejo when the
imported spec matches — verified against Forgejo 16 by the importer's
tests.

## What to finish by hand

- **Users** are imported as `Observe`: never modified, only resolved, so
  teams and repositories can reference them. With `--manage-users` they
  become `Manage`; a local account is then marked `bot: true`, because
  its password can't be known — the operator never resets it. Turning
  such a user into a regular local user (`bot: false` + `secretTargets`)
  **resets its password** into the targets.
- **Webhook secrets** are write-only in Forgejo. An imported hook keeps
  its current secret until you add a `secretRef`; add it before changing
  anything else on the hook, so every update carries the secret.
- **Organization owners** (`ownerRef`) only matter at creation and are
  left unset.
- **Allow-list**: once a `ForgejoNamespacePolicy` exists, the import
  namespace must be allowed for the imported organizations
  ([The allow-list](/docs/guides/allow-list)).
