---
title: Migrate an existing Forgejo
description: Bring users, organizations, teams, repositories, webhooks and deploy keys that already exist under the operator with the importer.
---

If your Forgejo already has users, organizations and repositories, the
operator won't touch them on its own. A CR whose name is already taken in
Forgejo stays `Ready: False` with reason `ForgejoObjectAlreadyExists`, so the
operator never takes over an object by accident.

To bring existing objects under management, use **`weebo-forgejo-importer`**.
It reads the live instance and creates the matching CRs **with each Forgejo id
already recorded in their status**. The operator then manages that exact
object instead of trying to create a new one.

## Before you begin

- The operator is [installed](/docs/guides/install) and a `ForgejoInstance`
  is [connected](/docs/guides/connect-instance).
- A **site-administrator token** for the importer (read access is enough).
- For `--apply`, a kube context allowed to create the CRs and patch their
  `status`: cluster-admin, or the [least-privilege role](#importer-rbac)
  below.
- If a [`ForgejoNamespacePolicy`](/docs/guides/allow-list) exists, the
  import namespace must be allowed for the imported organizations.

## What gets imported

| Forgejo | CR | Notes |
| --- | --- | --- |
| Users | `ForgejoUser` | As `managementPolicy: Observe` by default ([see below](#finish-by-hand)) |
| Organizations | `ForgejoOrganization` | |
| Teams and their members | `ForgejoTeam` | Except `Owners`, which Forgejo manages |
| Repositories | `ForgejoRepository` | Settings, units, branch protections and team access. Pull mirrors keep their `migrate.mirrorInterval`. |
| Repository and organization webhooks | `ForgejoWebhook` | Without `secretRef` ([see below](#finish-by-hand)) |
| Deploy keys | `ForgejoDeployKey` | With their `publicKey` |

**Not imported:** OAuth2 applications and access tokens. Forgejo never returns
their secrets, so the operator could never hand them out. Recreate them as new
CRs ([Credentials](/docs/guides/credentials)).

Every imported CR gets **`deletionPolicy: Orphan`**: these objects existed
before the operator, and deleting a manifest must not destroy them. Switch a
CR to `Delete` once you want that.

## Run the importer

The importer ships in the operator image. Run it from a workstation with
your kubeconfig mounted. A small shell function keeps the commands below
short (use `podman` instead of `docker` if that's what you have):

```bash
export FORGEJO_TOKEN=<site-admin-token>

importer() {
  docker run --rm -e FORGEJO_TOKEN \
    -v "$HOME/.kube/config:/kubeconfig:ro" -e KUBECONFIG=/kubeconfig \
    --entrypoint /usr/local/bin/weebo-forgejo-importer \
    ghcr.io/batleforc/weebo-forgejo-operator:<version> "$@"
}
```

| Flag | Default | Description |
| --- | --- | --- |
| `--url` / `FORGEJO_URL` | | Instance URL, as in `ForgejoInstance.spec.url` |
| `--token` / `FORGEJO_TOKEN` | | Site-administrator token |
| `--namespace`, `-n` | `default` | Namespace for repositories, webhooks and deploy keys |
| `--instance-ref` | none | Written as `spec.instanceRef` on every CR |
| `--owner` (repeatable) | everything | Only these organizations/users and their repositories. Other users are imported only when a team or repository references them. |
| `--manage-users` | off | Import users as `Manage` instead of `Observe` |
| `--apply` | off | Create the CRs and seed their status. Without it, the YAML is printed. |

Warnings, such as a team member that isn't a known user or a team left out of
a repository's `teamRefs`, are printed to stderr.

## Adopt safely: review, apply, then commit

`status` is a [subresource](https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#status-subresource):
`kubectl apply` and GitOps tools never write it. That's why the adoption
happens in the cluster, once, before the manifests go to Git.

<Steps>
<Step>

### Review

Print what would be imported, without touching the cluster:

```bash
importer --url https://git.example.com --namespace forgejo --owner weebo > forgejo.yaml
```

</Step>
<Step>

### Adopt

Run the same command with `--apply`:

```bash
importer --url https://git.example.com --namespace forgejo --owner weebo --apply
```

Each CR is created paused, with the `forgejo.weebo.io/import-pending`
annotation. Its `status.forgejoId` and `forgejoName` are written, and only
then is the annotation removed. The operator never sees an imported CR
without its id, so it can't create a duplicate.

</Step>
<Step>

### Commit

Commit `forgejo.yaml` to your GitOps repository. Its `status` blocks are
ignored when applied; the CRs already exist with their ids.

</Step>
<Step>

### Check

```bash
kubectl get fjorg,fjteam,fjuser
kubectl -n forgejo get fjrepo,fjhook,fjdkey
```

Everything should read `READY True`. The first reconcile of an adopted CR
sends nothing to Forgejo when the imported spec matches.

</Step>
</Steps>

<Accordions>
<Accordion title="Running the importer more than once">

Re-running `--apply` is safe:

- A CR that already owns the same object is skipped. If an earlier run
  stopped before removing the pause annotation, the CR is unpaused.
- A CR that owns a *different* object is reported as an error and left
  untouched.
- A CR that existed *without* an id (for example one stuck on
  `ForgejoObjectAlreadyExists`) is taken over and adopted.

</Accordion>
<Accordion title="How CR names are chosen">

CR names are the Forgejo names made valid for Kubernetes: lowercase, `_` → `-`,
and a repository like `weebo/.profile` becomes `weebo.profile`. The Forgejo id
is appended when two names clash.

With `--apply`, the importer first reads the CRs already in the cluster. An
object adopted by an earlier run keeps its CR name, and a name already owned
by another object is never reused, so runs with different `--owner`
selections don't collide.

Without `--apply` the cluster isn't read. On a cluster that already holds
imported CRs, export the manifests from the cluster (`kubectl get … -o yaml`)
rather than from a fresh print.

</Accordion>
</Accordions>

## Importer RBAC

Without `--apply` the importer never talks to the cluster. With it, it
reads the existing CRs (to keep names stable), creates the new ones by
server-side apply, seeds their `status` and removes the pause annotation.
It never reads or writes Secrets. A dedicated identity needs no more than:

```yaml
# Cluster-scoped kinds: users, organizations, teams.
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: weebo-forgejo-importer
rules:
  - apiGroups: ["forgejo.weebo.io"]
    resources: [forgejousers, forgejoorganizations, forgejoteams]
    verbs: ["get", "list", "create", "patch"]
  - apiGroups: ["forgejo.weebo.io"]
    resources: [forgejousers/status, forgejoorganizations/status, forgejoteams/status]
    verbs: ["patch"]
---
# Namespaced kinds, bound only in the import namespace (--namespace).
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: weebo-forgejo-importer-namespaced
rules:
  - apiGroups: ["forgejo.weebo.io"]
    resources: [forgejorepositories, forgejowebhooks, forgejodeploykeys]
    verbs: ["get", "list", "create", "patch"]
  - apiGroups: ["forgejo.weebo.io"]
    resources: [forgejorepositories/status, forgejowebhooks/status, forgejodeploykeys/status]
    verbs: ["patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: weebo-forgejo-importer
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: weebo-forgejo-importer
subjects:
  - kind: ServiceAccount        # or the User/Group running the importer
    name: weebo-forgejo-importer
    namespace: forgejo
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: weebo-forgejo-importer
  namespace: forgejo            # the --namespace you import into
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: weebo-forgejo-importer-namespaced
subjects:
  - kind: ServiceAccount
    name: weebo-forgejo-importer
    namespace: forgejo
```

Patching `status` is what lets it adopt an object: keep this role off
anyone who shouldn't be able to point a CR at an arbitrary Forgejo object,
and remove the binding once the migration is done. Namespaced CRs still go
through the admission webhook, so the [allow-list](/docs/guides/allow-list)
applies to the import namespace.

## Finish by hand

- **Users** are imported as `Observe`: they're never modified, only looked
  up, so teams and repositories can reference them.
  - With `--manage-users` they become `Manage`. A local account is then
    marked `bot: true`, because its password can't be known, and the
    operator never resets it.
  - Turning such a user into a regular local user (`bot: false` plus
    `secretTargets`) **resets its password** into the targets.
- **Webhook secrets** are write-only in Forgejo. An imported hook keeps its
  current secret, and edits leave it alone. Adding a `secretRef` recreates
  the hook with that secret, which loses its delivery history.
- **Organization owners** (`ownerRef`) only matter at creation, so they're
  left unset.
