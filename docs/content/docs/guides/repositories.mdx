Repositories and what hangs off them (webhooks, deploy keys) are
**namespaced**: they live next to the application that owns them. The
[allow-list](/docs/guides/allow-list) decides which organizations a namespace
may use.

| Kind | Short name |
| --- | --- |
| `ForgejoRepository` | `fjrepo` |
| `ForgejoWebhook` | `fjhook` |
| `ForgejoDeployKey` | `fjdkey` |

## Before you begin

- A `ForgejoOrganization` or `ForgejoUser` CR to own the repository (see
  [Users, OIDC and teams](/docs/guides/users-and-oidc)).

## Create a repository

A repository is created in one of three ways. The choice only applies at
creation; changing it afterwards has no effect.

<Tabs items={['Empty (init)', 'From a template', 'Mirror or migrate']}>
<Tab value="Empty (init)">

```yaml
apiVersion: forgejo.weebo.io/v1alpha1
kind: ForgejoRepository
metadata:
  name: app
  namespace: team-a
spec:
  organizationRef: { name: weebo }   # or userRef: { name: alice }
  name: app
  private: true
  init: { readme: Default, license: MIT }
```

</Tab>
<Tab value="From a template">

```yaml
apiVersion: forgejo.weebo.io/v1alpha1
kind: ForgejoRepository
metadata:
  name: app
  namespace: team-a
spec:
  organizationRef: { name: weebo }
  name: app
  fromTemplate: { repositoryRef: { name: service-template } }
```

The template must be a `ForgejoRepository` **in the same namespace** with
`isTemplate: true`.

</Tab>
<Tab value="Mirror or migrate">

```yaml
apiVersion: forgejo.weebo.io/v1alpha1
kind: ForgejoRepository
metadata:
  name: upstream-lib
  namespace: team-a
spec:
  organizationRef: { name: weebo }
  name: upstream-lib
  migrate:
    cloneAddr: https://github.com/example/lib.git
    mirror: true                 # false = one-off copy
    mirrorInterval: 8h           # kept in sync after creation
    authSecretRef: { name: github, tokenKey: token }   # for private sources
```

The migration runs inside Forgejo while the operator waits, for up to 15
minutes.

</Tab>
</Tabs>

## Settings and lifecycle

These fields are kept in sync: description, website, visibility (`private`),
default branch, and `units` (issues, wiki, pull requests, projects, releases,
packages, actions). Leave a unit unset to keep Forgejo's default.

| To… | Do |
| --- | --- |
| Rename | Change `spec.name`. Forgejo keeps a redirect from the old name. |
| Transfer to another owner | Change `organizationRef`/`userRef` and add the `forgejo.weebo.io/allow-disruptive-update: "true"` annotation. |
| Archive | Set `archived: true`. An archived repository is left untouched until you unarchive it. |
| Delete | Delete the CR. With the default `deletionPolicy: Orphan`, the repository **stays** in Forgejo; set `Delete` to remove it. |

## Team access and branch protection

```yaml
spec:
  teamRefs:
    - name: weebo-devs           # the ForgejoTeam CR's name
  branchProtections:
    - ruleName: main
      enablePush: true
      pushWhitelistTeams: [devs] # the team's name in Forgejo
      requiredApprovals: 1
      statusCheckContexts: [ci/build]
```

Both lists are authoritative: what isn't listed is removed.

- **`teamRefs`** grants teams access to the repository. They must belong to
  the owning organization. The access level comes from the team (see
  [Team access levels](/docs/guides/users-and-oidc#team-access-levels)). Forgejo always grants the `Owners` team and
  teams with `includesAllRepositories`; the operator leaves those alone.
- **Branch protection allow-lists** (`pushWhitelistTeams`,
  `pushWhitelistUsernames`…) use **Forgejo names**, not CR names, because
  they're passed to Forgejo as-is. In the example, the CR `weebo-devs` is the
  Forgejo team `devs`.
- A team only stays in a push allow-list if it has access to the repository.
  The operator syncs `teamRefs` first, so listing the team in both places is
  enough.

## Webhooks

```yaml
apiVersion: forgejo.weebo.io/v1alpha1
kind: ForgejoWebhook
metadata:
  name: app-ci
  namespace: team-a
spec:
  repositoryRef: { name: app }       # or organizationRef for an org-wide hook
  url: https://ci.example.com/hooks/forgejo
  events: [push, pull_request]
  secretRef: { name: app-ci-webhook, key: hmac }
```

Forgejo signs each delivery with the HMAC secret from `secretRef`. Things to
know:

- **Changing the Secret's value is detected.** Forgejo never returns the
  secret, so the operator tracks a hash of it (`status.appliedSecretHash`).
- **Some changes recreate the hook.** Forgejo's hook edit ignores the
  secret, `httpMethod` and any config key it doesn't return. Changing,
  adding or removing one of them deletes and recreates the hook, which gets
  a new id and **loses its delivery history**.
- **The authorization header** (`authorizationHeaderSecretRef`) is edited in
  place.

## Deploy keys

```yaml
apiVersion: forgejo.weebo.io/v1alpha1
kind: ForgejoDeployKey
metadata:
  name: app-ci
  namespace: team-a
spec:
  repositoryRef: { name: app }
  readOnly: true
  secretTargets: [{ name: app-deploy-key }]
```

- **Generated key.** Without `publicKey`, the operator generates an ed25519
  pair and the Secret gets `ssh-privatekey` and `ssh-publickey`, the key
  names of a `kubernetes.io/ssh-auth` Secret.
- **Your own key.** Set `publicKey` and the operator only registers it.
- **Rotation.** Deleting the Secret, or setting a new value on the
  `forgejo.weebo.io/rotate-secret` annotation, generates a fresh pair:

  ```bash
  kubectl -n team-a annotate fjdkey app-ci \
    forgejo.weebo.io/rotate-secret=$(date +%s) --overwrite
  ```

To give a *user* (such as a bot) an SSH key instead of a single repository,
use [`ForgejoUserKey`](/docs/guides/users-and-oidc#ssh-keys-for-a-user).
